## Context

The daemon currently admits only socket peer addresses in Tailscale's IPv4
CGNAT range, accepting both dotted-quad and IPv6-mapped IPv4 presentations.
That behavior matches the durable CIDR requirement, but the requirement did not
say whether raw tailnet IPv6 was deliberately unsupported. The implementation
also collapses malformed/missing peer data, unsupported families, and
out-of-range IPv4 into one diagnostic.

This boundary protects a bearer-authenticated daemon with read access to every
registered project. The change must therefore explain the unsupported upstream
configuration without widening access, trusting forwarding headers, logging
client addresses, or revealing admission rules over HTTP.

## Goals / Non-Goals

**Goals:**

- Make the existing IPv4-only policy explicit.
- Preserve the accepted address set exactly.
- Distinguish `unsupported-family`, `outside-range`, and
  `address-unavailable` in daemon diagnostics.
- Keep all refusal classes private to correlated daemon logs.
- Treat `::1` as loopback, `::` as an enforced all-interfaces bind, and other
  explicit non-loopback IPv6 literals as fail-fast while enforcement is enabled.
- Preserve explicit IPv4 and IPv6 bind inputs and document the IPv6-only-node
  workaround.

**Non-Goals:**

- Admit `fd7a:115c:a1e0::/48` or any other IPv6 range.
- Change explicit-address bind parsing or add a generic overlay mode.
- Change CIDR opt-out behavior or its default.
- Trust proxy/forwarding headers.
- Return refusal classifications or client addresses to any caller.

## Decisions

### 1. Keep the boundary IPv4 CGNAT-only

Where CIDR enforcement is enabled, the accepted set remains `100.64.0.0/10`,
after normalising IPv6-mapped IPv4. Raw IPv6 is unsupported even when it belongs
to Tailscale's reserved ULA prefix. Operators using the supported tailnet
boundary with an IPv6-only Tailscale configuration must leave IPv4 enabled on
both the daemon and client nodes.

**Rejected: admit the fixed Tailscale IPv6 `/48` now.** This would widen the
security boundary without evidence from a device that cannot use the documented
IPv4 path. It belongs in a separate reviewed change if that evidence appears.

### 2. Separate classification from the admission result

Address handling will produce one internal classification:
`accepted`, `unsupported-family`, `outside-range`, or
`address-unavailable`. IPv6-mapped values are normalised before classification,
so `::ffff:8.8.8.8` is `outside-range`.

The middleware converts every refusal classification to the same existing
public response. It logs only the classification and request correlation ID.
That identifier is Hono context variable `requestId`, generated by the existing
request-ID middleware before CIDR middleware runs and already carried by the
public error envelope. No new identifier, header, or correlation subsystem is
introduced.

**Rejected: expose a distinct response code or field.** That would let rejected
or authenticated callers probe the boundary's decision rule.

**Rejected: keep one undifferentiated diagnostic.** It makes malformed socket
state indistinguishable from an intentional family/range refusal and leaves the
policy difficult to operate.

### 3. Bind configuration, not request source, selects enforcement

Default `127.0.0.1` mode does not install CIDR middleware. For explicit IP
literals, `127.0.0.1` and `::1` are loopback; every other literal is
non-loopback. `tailscale`, `0.0.0.0`, and explicit non-loopback literals install
CIDR middleware unless the explicit opt-out is used, even when an individual
request has a loopback source. Because raw IPv6 is outside that admission set, a
specific non-loopback IPv6 bind with enforcement enabled fails before server
startup with a diagnostic directing the operator to the IPv4 path or the
existing explicit opt-out. With the opt-out it binds normally. Dual-stack
wildcard `::` is the exception: it starts with enforcement, admits mapped CGNAT
IPv4 peers, refuses raw IPv6 peers as `unsupported-family`, and prints the
all-interfaces warning just as `0.0.0.0` does.

**Rejected: infer enforcement from each request address.** A loopback-source
request against an all-interface bind would bypass the configured boundary.

**Rejected: keep treating unrecognised IPv6 literals as loopback-equivalent.**
That lets a non-loopback bind omit the CIDR boundary. Classifying the configured
literal closes the gap without removing it from the CLI surface.

**Rejected: start an enforced non-loopback IPv6 server that refuses every
peer.** A clean startup on a specific IPv6 literal would misrepresent a
configuration that cannot carry the admitted IPv4 path. Failing before startup
makes the policy and remediation visible. This rejection does not apply to
dual-stack wildcard `::`, which can serve IPv6-mapped IPv4 peers.

### 4. Keep Tailscale setup failures distinct

`--bind tailscale` will distinguish a missing or unavailable Tailscale
installation from a running Tailscale node that has no CGNAT IPv4 address. Both
fail before server startup with operator-facing setup diagnostics; neither
changes request admission. This is a new behavior and therefore receives its
own RED/GREEN task rather than a green-on-first-run characterization test.

## Risks / Trade-offs

- **IPv6-only Tailscale configurations remain unsupported** → document the
  limitation and exact IPv4 workaround at the pairing/setup boundary.
- **Internal classes could leak through response drift** → assert identical
  status, public code, and response field sets for every refusal class.
- **Classification work could accidentally change admission** → pin the current
  accepted/refused address table with characterization tests before RED/GREEN.
- **Diagnostics could retain sensitive peer data** → log only the class and
  existing correlation ID; test that no client address appears.
- **A specific IPv6 bind could start but serve nobody** → fail before startup
  while enforcement is enabled and allow it through the existing explicit
  opt-out. Keep dual-stack `::` enforced and warn because it can serve mapped
  IPv4 peers.

## Migration Plan

1. Land characterization tests for current bind and address behavior.
2. Add the internal classifier through a failing diagnostic test.
3. Classify explicit IPv6 bind literals through a failing enforcement-selection
   test.
4. Route middleware diagnostics through the classifier without changing the
   public response.
5. Update operator documentation and the ADR.
6. Verify the accepted-address table is unchanged.

An existing specific non-loopback IPv6 bind must add the explicit CIDR opt-out
or move to the documented CGNAT IPv4 path; `::` remains startable with
enforcement. Rollback removes the classifier and documentation while leaving
the pre-existing IPv4-only admission behavior intact. No stored data or
wire-schema migration is required.
